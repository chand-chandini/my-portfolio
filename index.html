CASE STUDY / 01
01 / HOSTEL MANAGEMENT SYSTEM

What happens when two students try to book the same room?

Designing a hostel allocation system where the backend, not the interface, decides who gets the room.

Role Full Stack Developer
Frontend React + Vite
Backend Django REST
Database PostgreSQL
01

The problem

Hostel allocation involves more than displaying a list of rooms. Students need to register, authenticate, see available rooms and submit bookings.

The interesting problem appeared when thinking about multiple students attempting to book an available room at nearly the same time.

A frontend-only availability check is not enough. The server needs to make the final decision.

02

The architecture

Student
→
React
→
Axios
→
Django REST
→
PostgreSQL
03

The booking flow

When a student selects a room, the React application sends the selected room ID to the backend.

Django authenticates the request, identifies the student, retrieves the room and checks whether the booking is valid.

Select room
→
Authenticate
→
Lock room
→
Validate
→
Create booking
04

The engineering challenge

Imagine there is only one available bed.

Student A checks the room. Student B checks the room almost simultaneously.

If both requests simply read the same availability value before either request updates it, both could potentially proceed.

I therefore moved the critical decision into an atomic database transaction with row-level locking.

Django / booking logic 
with transaction.atomic():

    room = Room.objects.select_for_update().get(
        id=room_id
    )

    if room.is_full:
        reject_booking()

    Booking.objects.create(
        student=student,
        room=room
    )
05

Security & validation

Booking operations are protected behind authentication. The application uses JWT authentication to identify authenticated users.

The backend also validates the student and booking rather than trusting values sent by the frontend.

03 / BUS BOOKING SYSTEM

How do you keep seat availability accurate during booking?

Building a booking flow where the backend controls the state of available seats.

Role Full Stack Developer
Frontend React
Backend Django REST
Database SQL
01

The problem

A bus booking application needs to keep track of which seats are available, which seats are reserved, and which bookings have been cancelled.

The challenge is ensuring that the displayed seat state and the actual backend state remain consistent.

02

The booking flow

Search route
→
Select bus
→
View seats
→
Reserve
→
Confirm
03

Backend-controlled state

The frontend provides the interface for selecting seats, but the backend remains responsible for validating and updating booking information.

This separation makes the application more reliable than relying only on frontend state.

04

Cancellation

Cancellation is treated as another backend operation. When a booking is cancelled, the corresponding seat becomes available again through the application logic.
